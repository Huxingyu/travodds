# DataSharing 下一步推进计划（2026-10-29）

## 当前起点

实现基线：主工作树 `main@3da8e077b9902142cdb4549eafa5b43114bdf936`。DataSharing 已有共享段、原生 Loan、读写旁路、协商和部分故障回退，不能把已有原型等同于全部边界和验收口径已经确定。

现有通知采用 always-lock-free 的 32 位通知代次与 futex；槽位提交、注册和引用事务由 robust metadata mutex 保护。完整 publish/write 有锁。官方“无锁通知”的范围待对齐；以下更强的发布目标是我们的研究与改进目标，不冒充已确认的官方条款。

日志独立修复 PR：https://gitee.com/agiros/travodds/pulls/115 ，最新提交 `1edc5d9b6a4c8ac56a76db2295e7a1109d964136`。该分支与 DataSharing 主线分别推进。

## 本轮确定的顺序

| 顺序 | 工作 | 产出与完成条件 |
|---|---|---|
| 1 | 将现有发布/等待边界做成确定性实验 | 明确观察到锁依赖、通知竞争窗口、超时边界；区分当前行为记录与未来目标断言。 |
| 2 | 写清发布和 Loan 的不变量，建立独立的无锁提交原型 | 在既定单 Writer/多 Reader 模型下，暂停一个 Reader 不会因其持有元数据锁而阻塞 Writer 的其他可用槽位提交；没有空槽时允许明确的容量耗尽结果。 |
| 3 | 分离控制路径与提交路径 | 注册、取消、死亡回收和进程身份检测的慢工作不能被遗漏，也不能以“不在提交路径”为由破坏目标 Reader、session/generation 和引用安全。 |
| 4 | 集成并验证 QoS/回退 | 对 AUTO/ON、VOLATILE/TRANSIENT_LOCAL、普通 write/Loan 分别定义与验证行为，再接回 DDS/history 等现有锁体系。 |
| 并行维护项 | 按证据拆分现有库问题的独立修复 | 每项有原版失败、修复后通过、最小 diff；不把原型开发自身的问题当作上游已有 bug。 |

“独立原型”首先研究共享段提交，不等于承诺整个 DDS write 无锁。DDS 写锁、history 等待和混合路径序列化仍须分别描述。

## 第一批实验如何落地

现有 `test/unit_payloadpool/test_sharedpayloadpool.cpp` 已有 Mapping 辅助对象、子进程与通信设施，可以直接用于控制共享头和故障进程。新增用例应避免靠固定 sleep 猜中竞争窗口；用阶段屏障和外部 watchdog 保证可终止，并清理本用例创建的确切 session。

1. **存活持锁者暂停。**子进程先取得 metadata mutex 并报告阶段，再 SIGSTOP；调用线程执行 publish 或带超时的 loan/waitNext。验证当前调用仍受取锁阻塞影响；恢复子进程、正常解锁再检查结果。此用例首先记录现有边界，不能把它“观察到阻塞”记成未来无锁目标已通过，也不能用无期限 join 挂死整个测试。
2. **通知进入睡眠前的竞争。**确定性地控制 Reader 检查/采样与 futex 比较的窗口，在窗口内提交。验证 EAGAIN 后仍能按谓词取得数据。若必须设置测试钩子，应保持测试专用并避免正式热路径增加回调/锁。
3. **32 位代次与信号。**在受控条件下将 changed 置近 UINT32_MAX，验证正常回绕；注入等待线程 EINTR，确认重新检查谓词与原始 deadline。整圈 ABA 应单独以模拟验证，不能把槽位环绕或 64 位 token 边界测试充当代次回绕证明。
4. **提交阶段死亡。**在元数据事务开始前、修改中、提交后但 wake 前分别停住并终止持锁子进程，检查 CORRUPT、新借用拒绝、旧 Loan 字节保留和新 session 恢复的边界。不承诺 poisoned session 可原地自动修复。

## 原型必须保留的不变量

- 只有完成构造并提交的样本才能被 Reader 看到；明确提交线性化点与 release/acquire 关系。
- Writer/history 引用、未消费 Reader 引用、已借出 Reader Loan 任一仍有效时，槽位不能被覆盖。Reader 被暂停可以固定其槽位；这与暂停 Reader 持有全段锁而阻塞其他槽位提交不同。
- 槽位 generation、Reader 注册 generation 和 session 必须共同防止陈旧归还、陈旧注册及重启后误认；仅增加一个 atomic sequence 不足以自动保证这些条件。
- 固定预算内无可复用槽位时，允许返回容量耗尽或按已经定义的 API 策略等待；不分配隐藏槽位来掩盖背压。算法整体进展与每次发布都必须成功不是同一个要求。
- 注册/注销和死亡回收与提交并发时，不能遗漏目标、错误固定或过早清除 pin。不能把“加锁”简单替换成几个独立 atomic 操作。
- publish 成功后的可写 Loan 失效；共享提交不可撤销时，后续 RTPS 错误不得把可写所有权交还应用。

## 其他已确认的范围问题

keyed 首次注册的 Writer/Reader 键快照复制整个原生对象。短期准确记录该例外；若要消除完整对象复制，需增加或明确键专用表示/提取契约，验证 get_key_value、dispose/unregister 与重新注册。不能通过删除快照换取表面上的零 memcpy。

AUTO 的暂时映射/注册失败回退与重试已经存在；nativeCommit 失败、poisoned session、活持锁者暂停不是同一个故障类别。应先建立 QoS/调用方式矩阵，再决定哪些错误可重试 CDR，以及是否需要新的错误状态或重建策略。
